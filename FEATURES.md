## 2. Syntax highlighting

**Policy: the `by` LSP is the source of truth for semantic colour and is always preferred when
available.** It knows the types and symbols a token-stream heuristic can only guess at, and it
tracks the language on its own — new syntax colours with no plugin change. The lexer stays
regardless (the platform requires one to register the language, and semantic tokens never cover
strings, comments, numbers, operators or brackets).

There is no longer a no-LSP fallback for anything *semantic*, and that is deliberate: basedpython is
not usable without `by`, so an approximate second implementation bought nothing and cost a
permanent maintenance debt against a language that keeps moving. Without a server a `.by` file gets
lexical colour only. Don't reintroduce guessed semantic colour; fix the LSP path instead.

- [x] Lexer-driven keyword/string/number/comment/operator highlighting (needed in all modes)
- [x] basedpython extras (`?.`, `??`, `final`, `override`, `protocol`, `let`, `newtype`, `data class`, etc.) — lexer keyword set; a stale list is tolerable since the server reports keywords itself
- [x] ~~Annotator-level semantic coloring (builtins, self/cls, decorators, type names)~~ **removed**: every one of those is a question about what the code means, which `by` answers from real types and reports as a semantic token. `highlight.BasedPythonAnnotator` and `highlight.BasedPythonSoftKeywords` are gone; `highlight.StringEscapeAnnotator` keeps the one part a semantic token cannot carry (escapes inside a literal)

- [x] Trim margin for multiline strings — editor.highlight.StringMargins (pure) behind ByStringMarginPassFactory (a `highlightingPassFactory`) and ByStringMarginRenderer. basedpython trims a triple-quoted string like a Java text block, and that is a rule with no visible evidence in the source: the whitespace shared by every line belongs to the code's layout rather than to the string, so what the literal *contains* is decided by its least-indented line — from somewhere else in the literal, silently. IDEA answers the same rule in Java with a vertical line in the text block; this is that line for `.by`. The margin follows JLS 3.10.6 / `String::stripIndent`: every non-blank content line contributes its indentation, blank lines contribute nothing (they are erased, so they cannot pull it left), the line carrying the closing quotes contributes its own even though it is blank — which is what makes moving that line the way you set the margin — and the smallest wins. One shape had to be decided here because Java cannot write it: content on the opening line (`"""Summary.`, the ordinary docstring). That text starts immediately after the quotes, carries no indentation to measure and loses none, so it is excluded from the minimum exactly as `inspect.cleandoc` excludes it, and the margin is not drawn across it; in the shape Java *can* write the two rules coincide. A margin of zero is not drawn — nothing is stripped, and a rule against the left edge of the text would be marking that in the one place a reader cannot tell it from the editor's own border. The rule spans the lines of *text*: not the opening line, whose content starts after the quotes with nothing taken off it, and not a closing-quotes line of its own, which is the margin rather than something measured against it — a literal with no text at all (`"""` newline `"""`) therefore gets none. The geometry is measured in the renderer at paint time from the highlighter's *live* range, not carried in from the pass: a pass's offsets are a snapshot, the editor keeps painting between passes, and drawing from them put the rule where the text used to be on every keystroke and jumped it back a few hundred milliseconds later. For the same reason an edit inside a marked literal repaints the whole literal (a document listener installed per editor, disposed with it): the editor repaints the edited line, which is all it can know to do, and a rule that has just moved would leave the old column standing on the lines above. A pass rather than an annotator because there is nothing to attribute: text attributes colour characters, and this is a line on lines that may have no character at that column at all (a blank line in the literal, or closing quotes further right than the text above them). Placed by asking the editor where an offset is rather than by multiplying a column by a character width, on a line whose leading characters are known to be exactly the whitespace being stripped, so tabs, a proportional font and an inlay sitting in the line all come out right. Not something the server can answer: `by`'s semantic tokens and inlay hints both stop at the quotes — a string literal is one token, and nothing inside it is ever reported. Colour is `BASEDPYTHON_STRING_MARGIN`, a `ColorKey` (it is a line beside the text, not a way of drawing text, the same distinction the platform makes for indent guides), and undefined it is the scheme's `INDENT_GUIDE_COLOR`. That is not deference, it is the same line: a string's lines are an indented run, so the editor already rules an indent guide down them at the indentation they share — the trim column, by the same arithmetic — and measured off a rendered editor the two land on the same pixel column (which is what fixes the rule's x at two scaled points left of the anchor's cell, not taste). The platform draws its guide on a run's *interior* lines only and over the top of ours, so two colours at that column do not read as two lines: they read as one line that changes colour partway down, which is exactly what a string-coloured margin looked like. Taking the guide's colour and continuing it across the first and last content lines — which the guide skips — is what IDEA shows for a Java text block, and the margin still earns its keep: it reaches those lines, it is measured by the trim rule rather than by block indentation, and it holds where a blank line or an outdented closing quote leaves the guide with nothing to say
- [x] Matched-brace + same-keyword highlighting, and *Move Caret to Matching Brace* (`Ctrl+Shift+M`) across a whole compound statement — editor.highlight.BlockClauses (pure, text-based) behind editor.highlight.BasedPythonKeywordHighlightUsagesHandlerFactory (the highlighting) and editor.highlight.BasedPythonCodeBlockSupportHandler (the `codeBlockSupportHandler` EP, whose marker and block ranges are what `MatchBraceAction` navigates and what the identifier pass draws when no server claims the caret). Covers `if`/`elif`/`else`, `try`/`except`/`else`/`finally`, `for`/`while` … `else` and `match`/`case`; chains are grammar-checked rather than collected by keyword set, so two adjacent `if`s, or the `try` after an `else`, stay separate statements. `BlockClauses.familyAt` adds what a braced language gets from *Highlight exit points*: a `def` with its `return`s and `raise`s, a loop with its `break`s and `continue`s, each binding to the nearest enclosing block of its kind — so a nested `def` keeps its own `return`s, a `break` in a loop's `else` belongs to the loop outside it (the `else` is not the loop's body), and a `break` inside a nested `def` reaches no loop at all. A suite written on its head's own line (`if x: return 1`) is scanned as a line indented one past that head, so it is not a hole in the exits. These are highlighting only, not markers: a `return` does not delimit the block it leaves, and marker ranges are what `MatchBraceAction` navigates. Not something the server can answer: LSP has no paired-keyword request, and its one near neighbour `textDocument/documentHighlight` is specified for occurrences of a *symbol* — probed against `by ruff/0.0.1`, it returns `null` at every keyword position. PyCharm registers no `codeBlockSupportHandler` for Python either, so there was nothing to inherit. The highlight factory is `order="first"`, ahead of the platform's `LspHighlightUsagesHandlerFactory`, which claims every caret in a `.by` file because `by` advertises `documentHighlightProvider` and then highlights nothing on a keyword

## 3. LSP — `by` server
- [x] Server descriptor, start/stop, supported extensions — `.by`/`.byi`/`.py`/`.pyi`, **plus django templates**: `.html`/`.htm`/`.txt`/`.xml`/`.django`/`.dj` under a `templates/` directory, matching django's own app-directories convention and the rule the server documents. Gated on the project carrying a basedpython marker, because `.html` is the most common extension there is; `buff` is unchanged and stays python-only
  - [ ] Ask the server which documents it serves, rather than duplicating its rule. Not possible today: LSP has no such request, the only file scoping in the protocol is a `documentSelector` on a *dynamic* registration, and `by` registers nothing for text documents — probed against 0.0.1, `initialize` returns `capabilities` and `serverInfo` with no `experimental` block, and its one registration is `didChangeWatchedFiles` with `globPattern: "**"`. It would also arrive too late, since this is what decides whether to start a server at all. One case the duplicated rule gets wrong meanwhile: a `TEMPLATES[*]["DIRS"]` pointing somewhere not called `templates` is served by the server and not offered by the plugin. Needs the server to advertise a document selector
- [x] Completion, hover, goto def/decl/type, references, rename, signature help, diagnostics, inlay hints, semantic tokens, code actions, symbols, folding, type hierarchy
- [x] **Push-to-hint** — each kind of hint is *never*, *always*, or *only while a key is held*, the gesture Rider calls Push-to-Hint and VS Code spells `editor.inlayHints.enabled: offUnlessPressed`. Two settings over the same kinds rather than one switch, because the kinds are not read the same way: a parameter name is worth having in front of you, a `: T` on every binding is what most people want only when they are asking. Holding the key shows the union of both. The key is a modifier held, not a shortcut pressed, so it is not a keymap action — the action system only ever reports the press, and a binding here would swallow the keystroke from whatever else wanted it. `lsp.inlay.ByHintPush` (an app service) watches `getModifiersEx` on every input event through one `IdeEventQueue` dispatcher that never consumes anything, publishes the raw mask, and lets each hint decide with its own project's `ByPushKey` — so a split, a second project window and a differently-configured project all behave. Default `Ctrl+Alt` (VS Code's), the shortest combination that means nothing on its own in an editor; plain `Ctrl` is the platform's go-to-declaration underline. Instant both ways: an on-push hint's inlay is built with the rest of them and merely draws nothing until the key goes down (`ByInlayHintPresentation.shown` → `fireSizeChanged` → `Inlay.update()`), because the alternative — collecting on press and release — is a daemon pass and a round trip to `by` per keystroke, and the platform's inlay pass skips a file whose PSI has not changed at all. A hidden hint measures one pixel, the editor rejecting a zero-width inline element outright
- [x] A setting per kind of hint `by` computes, taken from the server rather than guessed at: `ty_ide::InlayHintKind` is what it builds and `InlayHintOptions` in `ty_server` is what it lets a client switch, and `lsp.inlay.ByHintKind` mirrors that list option for option (variable types, lambda parameter types, call type arguments, type argument names, numeric promotions, revealed types, inferred raises, call argument names, implicit parameters, implicit self, implicit arguments, inferred override, inferred variance, inferred reification), plus an *other* kind of the plugin's own so a hint a newer `by` sends is switchable the day it appears. **Never is enforced at the server**: the modes go out as `initializationOptions.inlayHints.*`, so a hint nobody will draw is not inferred rather than inferred and dropped (`by` has no `workspace/didChangeConfiguration` yet, so a change restarts the server — which is what the settings page already did, and what `by`'s own VS Code extension does). **Always against on push is client-side**, because LSP carries two kinds for the fourteen the server distinguishes: `ByInlayHints.shapeOf` recovers the rest from the label, which works because the labels are fixed strings (` raises T`, `  revealed: T`, `override `, `reified `, `out `/`in `, `[T]`, `: T`, `name=`) and the two LSP kinds separate `name=` on an argument from `T=` on a type argument. Two kinds `by` writes identically (a variable's type and a lambda parameter's; an implicit `self` and any other implicit parameter) cannot be told apart on the wire, so where their settings disagree the more visible one draws — see `ByHintModes.forShape`. The django-template kinds (`templateBindingTypes`, `resolvedTemplates`) are deliberately absent: this provider draws hints for basedpython files, and the platform's own LSP rendering, which would draw them in an `.html` template, is off for `by`. There is no return-type setting because `by` has no return-type hint — the old toggle stood for nothing
- [x] Inlay hints rendered in the **editor font**, at editor size, on the code's baseline, faded onto a faint tint of the editor background — the VS Code look, and a deliberate replacement of the platform's. The platform builds every LSP hint with `PresentationFactory.smallText`: UI label font at ~⅘ editor size inside a rounded grey pill. For a language whose hints are nearly all types that reads as something pasted onto the line rather than as the annotation it stands in for. `LspInlayHintCustomizer` can only enable, disable or filter — there is no hook for the presentation — so `lsp.inlay.ByInlayHintsProvider` (a `codeInsight.inlayProvider`) sends `textDocument/inlayHint` itself and paints through `ByInlayHintPresentation`, and `ByLspServerDescriptor` sets `LspInlayHintDisabled` so the two don't both draw. Disabling costs nothing on the wire: the `inlayHint` *client capability* is advertised unconditionally by the platform, so `by` still answers. Font and size come from the *editor's* scheme, so zoom / presentation mode / distraction-free carry the hints with them — which the platform's rendering cannot do, its font being the single global `Use editor font` checkbox. Colour is `BASEDPYTHON_INLAY_HINT` — **both** halves. Faded text alone was a bug, not a style: dimmed editor-font text is how the IDE draws code that does not run, so an untinted hint is indistinguishable from an unused import sitting on the same line (`unused_local: int` had the name and the hint in the same grey). The tint is the smallest mark that separates them, and is not the platform's opaque capsule — it is sized to the text box rather than the line box, barely rounded, and leaves the glyphs on the code's column. Both bundled schemes set the pair; any other scheme gets them derived — text faded 38% into the background, tint the background with 20% of that text colour mixed in, resolved per half so a theme that restyles only the text still gets a tint derived from *its* colour. Not registered under `Settings | Editor | Inlay Hints` on purpose (`isVisibleInSettings = false`): the three basedpython settings are the one source of truth
- [x] A record of what the inlay pass did, and a check for a hint drawn twice — `lsp.inlay.ByInlayAudit` (pure) behind `ByInlayAuditLog` (an app service), `ByInlayAuditListener` (a `DaemonListener`) and *Tools | basedpython | Dump Inlay Hint Record*. A doubled hint (`def f() → 1 → 1:`) has exactly three possible causes and they are indistinguishable on screen: the collector ran twice in one pass, `by` sent the hint twice in one reply, or the platform is holding an inlay the pass never handed it. Nothing can be told after the fact either — a presentation carries no history, and the next pass drops the extra silently (`InlayHintsUtils.produceUpdatedRootList` keeps as many as the new list has), which is what let the first of the three live for as long as it did. So each pass records the hints it added, which run of the collector added each one and where it sat in `by`'s reply, and the audit reads that against what the editor is drawing — read through the renderers' own `toString`, which is public API and answers with the presentations joined (`LinearOrderInlayRenderer` → `SequencePresentation` → `[a b]`, the wrappers in between delegating down to `ByInlayHintPresentation.toString`), so an inlay holding two copies says so without reflection or a `@TestOnly` accessor. Drawn *fewer* times than collected is never a finding: an inlay can be waiting for a repaint or sitting at an offset an edit has moved, and neither is the bug. The daemon's finish is when the check runs — the only event that follows every way hints can change, with the pass applied by then — and it writes only when something is doubled, once per set of findings, because the daemon finishes far more often than the inlay pass runs. The action exists for the case the listener cannot serve: a doubling already on screen, which no further daemon run is coming for. Nothing is de-duplicated on the way in — a hint `by` sent twice is added twice, since quietly dropping it would hide the bug in the one place that can tell it apart from the other two
- [x] Call hierarchy (LSP — enabled on `by`)
- [ ] Document link support — left enabled on the `by` client, but `by` advertises no `documentLinkProvider` (checked against 0.0.1a9: 25 capabilities, not one of them document links), so nothing is ever requested and the feature does not exist. Harmless as configured; it becomes real if and when the server grows the capability
- [x] Code lens (run/references counts) — `by` LSP codeLens enabled
- [x] Pull-diagnostics workspace mode — platform LSP integration consumes `by` pull diagnostics when the server advertises them, surfacing them in the editor + Problems tool window and feeding WolfTheProblemSolver (project-view error stripes / red filenames) automatically; no extra wiring required
- [x] **A diagnostic's tooltip reads as the message it is** — `markup.ByCodeSpans` behind `lsp.diagnostics.ByDiagnosticsSupport` (on `by` and on `buff`, whose messages are written the same way). Every message the type checker writes names its types in markdown code spans, and the platform hands the message to `AnnotationBuilder.tooltip` unchanged — which takes HTML. So ``Object of type `<class 'int'>` is not callable`` reached the user as *Object of type `` `` is not callable*: the backticks shown as backticks, the type itself eaten by Swing's HTML parser as an unknown tag. The tooltip is now escaped, with a `<code>` per span; the *message* is untouched, since that is the plain-text side — Problems view, error stripe, *Copy problem description* — where backticks are simply how a type is quoted. Pairing the delimiters cannot be exact and does not pretend to be: `ty` never escapes the backticks that come out of the code being checked, so ``Type `Literal["`"]` is not assignable to `str` `` is genuinely ambiguous. Three rules bound the damage instead — a run matches a run of its own length (CommonMark, so a producer that *does* escape is read correctly), a span never crosses a line (one stray backtick can only spoil its own line), and a closer that would leave a `"` open is passed over for the next one, which recovers exactly the `Literal["`"]` case above and falls back to CommonMark's answer when no closer does better. The text is never altered or dropped, so the worst case is a fragment styled as prose that should have been code. The same renderer marks up the docstring in Type Info (`Ctrl+Shift+P`) — but not the type block above it, where a backtick is a character in a python string — and the two `by explain rule` balloons

- [x] **`main`'s parameters, asked for as a form** — a top-level `main` *is* the program's command-line interface: basedpython builds an argparse parser from the signature (`str`/`int`/`float`/`bool`/`Path`, `bool` as a `--flag` / `--no-flag` pair, an underscore accepted both as `--out-dir` and `--out_dir`) and appends the guard that feeds it.   - Asked **once per program**, not once per run: the answer is remembered against the module, and `ByRunFromFileProducer` seeds the next context configuration from it, so the green icon stays one click and runs the program the way it was last run. Discovery is nine file names read at the project root — no process is started to enumerate tasks, unlike the test view's `by run pytest --collect-only` — so a VFS listener re-scans on save (500 ms debounce) and the tool window makes itself available when a project grows its first config file
  - Commands are one place (`ByTaskCommands`, pure + tested): `pre-commit run <id>`, `prek run <id>` (the two differ in exactly one flag — `--hook-stage` vs `--stage` — which is why they are separate runners), `lefthook run <hook> --commands|--jobs <name> --no-tty`, `./pw <alias>`. A hook whose `stages:` exclude `pre-commit` carries its stage into the command, since a plain `run <id>` would skip it silently with a zero exit code. A lefthook `scripts:` entry has no CLI filter to select it (there is no `--scripts`), so its row runs the whole hook and says so in grey
  - Config files are parsed by hand (`ByYaml`, `ByToml`) rather than through the YAML/TOML PSI: the scan is a pure function of file text on a background thread, which is what makes it testable against real configuration and free of read actions. Both document what they do not do (anchors/aliases/multi-document, dotted keys/array-of-tables) — none of it reachable from these schemas
  - Runners resolve through `ByEnvironments.resolve`, so a project's own `.venv/bin/pre-commit` beats a global install; pyprojectx is the exception and runs the checked-in `./pw` (chmod-ed via `Executables` if the mode bit was lost), falling back to `px` on `PATH`. `.pre-commit-config.yaml` is offered under `prek` when that is the only one of the two installed (`ByTaskRunners.preferred`)
  - *All files* is a persisted project preference, defaulted on: a hook run from a tool window with nothing staged inspects nothing and reports success
