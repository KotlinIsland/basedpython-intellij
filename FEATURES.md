## 2. Syntax highlighting

**Policy: the `by` LSP is the source of truth for semantic colour and is always preferred when
available.** It knows the types and symbols a token-stream heuristic can only guess at, and it
tracks the language on its own — new syntax colours with no plugin change. The lexer stays
regardless (the platform requires one to register the language, and semantic tokens never cover
strings, comments, numbers, operators or brackets).

There is no longer a no-LSP fallback for anything *semantic*, and that is deliberate: basedpython is
not usable without `by`, so an approximate second implementation bought nothing and cost a
permanent maintenance debt against a language that keeps moving. Without a server a `.by` file gets
lexical colour only. Don't reintroduce guessed semantic colour; fix the LSP path instead.

- [x] ~~Annotator-level semantic coloring (builtins, self/cls, decorators, type names)~~ **removed**: every one of those is a question about what the code means, which `by` answers from real types and reports as a semantic token. `highlight.BasedPythonAnnotator` and `highlight.BasedPythonSoftKeywords` are gone; `highlight.StringEscapeAnnotator` keeps the one part a semantic token cannot carry (escapes inside a literal)

- [x] Trim margin for multiline strings — editor.highlight.StringMargins (pure) behind ByStringMarginPassFactory (a `highlightingPassFactory`) and ByStringMarginRenderer. basedpython trims a triple-quoted string like a Java text block, and that is a rule with no visible evidence in the source: the whitespace shared by every line belongs to the code's layout rather than to the string, so what the literal *contains* is decided by its least-indented line — from somewhere else in the literal, silently. IDEA answers the same rule in Java with a vertical line in the text block; this is that line for `.by`. The margin follows JLS 3.10.6 / `String::stripIndent`: every non-blank content line contributes its indentation, blank lines contribute nothing (they are erased, so they cannot pull it left), the line carrying the closing quotes contributes its own even though it is blank — which is what makes moving that line the way you set the margin — and the smallest wins. One shape had to be decided here because Java cannot write it: content on the opening line (`"""Summary.`, the ordinary docstring). That text starts immediately after the quotes, carries no indentation to measure and loses none, so it is excluded from the minimum exactly as `inspect.cleandoc` excludes it, and the margin is not drawn across it; in the shape Java *can* write the two rules coincide. A margin of zero is not drawn — nothing is stripped, and a rule against the left edge of the text would be marking that in the one place a reader cannot tell it from the editor's own border. The rule spans the lines of *text*: not the opening line, whose content starts after the quotes with nothing taken off it, and not a closing-quotes line of its own, which is the margin rather than something measured against it — a literal with no text at all (`"""` newline `"""`) therefore gets none. The geometry is measured in the renderer at paint time from the highlighter's *live* range, not carried in from the pass: a pass's offsets are a snapshot, the editor keeps painting between passes, and drawing from them put the rule where the text used to be on every keystroke and jumped it back a few hundred milliseconds later. For the same reason an edit inside a marked literal repaints the whole literal (a document listener installed per editor, disposed with it): the editor repaints the edited line, which is all it can know to do, and a rule that has just moved would leave the old column standing on the lines above. A pass rather than an annotator because there is nothing to attribute: text attributes colour characters, and this is a line on lines that may have no character at that column at all (a blank line in the literal, or closing quotes further right than the text above them). Placed by asking the editor where an offset is rather than by multiplying a column by a character width, on a line whose leading characters are known to be exactly the whitespace being stripped, so tabs, a proportional font and an inlay sitting in the line all come out right. Not something the server can answer: `by`'s semantic tokens and inlay hints both stop at the quotes — a string literal is one token, and nothing inside it is ever reported. Colour is `BASEDPYTHON_STRING_MARGIN`, a `ColorKey` (it is a line beside the text, not a way of drawing text, the same distinction the platform makes for indent guides), and undefined it is the scheme's `INDENT_GUIDE_COLOR`. That is not deference, it is the same line: a string's lines are an indented run, so the editor already rules an indent guide down them at the indentation they share — the trim column, by the same arithmetic — and measured off a rendered editor the two land on the same pixel column (which is what fixes the rule's x at two scaled points left of the anchor's cell, not taste). The platform draws its guide on a run's *interior* lines only and over the top of ours, so two colours at that column do not read as two lines: they read as one line that changes colour partway down, which is exactly what a string-coloured margin looked like. Taking the guide's colour and continuing it across the first and last content lines — which the guide skips — is what IDEA shows for a Java text block, and the margin still earns its keep: it reaches those lines, it is measured by the trim rule rather than by block indentation, and it holds where a blank line or an outdented closing quote leaves the guide with nothing to say
- [x] Matched-brace + same-keyword highlighting, and *Move Caret to Matching Brace* (`Ctrl+Shift+M`) across a whole compound statement — editor.highlight.BlockClauses (pure, text-based) behind editor.highlight.BasedPythonKeywordHighlightUsagesHandlerFactory (the highlighting) and editor.highlight.BasedPythonCodeBlockSupportHandler (the `codeBlockSupportHandler` EP, whose marker and block ranges are what `MatchBraceAction` navigates and what the identifier pass draws when no server claims the caret). Covers `if`/`elif`/`else`, `try`/`except`/`else`/`finally`, `for`/`while` … `else` and `match`/`case`; chains are grammar-checked rather than collected by keyword set, so two adjacent `if`s, or the `try` after an `else`, stay separate statements. `BlockClauses.familyAt` adds what a braced language gets from *Highlight exit points*: a `def` with its `return`s and `raise`s, a loop with its `break`s and `continue`s, each binding to the nearest enclosing block of its kind — so a nested `def` keeps its own `return`s, a `break` in a loop's `else` belongs to the loop outside it (the `else` is not the loop's body), and a `break` inside a nested `def` reaches no loop at all. A suite written on its head's own line (`if x: return 1`) is scanned as a line indented one past that head, so it is not a hole in the exits. These are highlighting only, not markers: a `return` does not delimit the block it leaves, and marker ranges are what `MatchBraceAction` navigates. Not something the server can answer: LSP has no paired-keyword request, and its one near neighbour `textDocument/documentHighlight` is specified for occurrences of a *symbol* — probed against `by ruff/0.0.1`, it returns `null` at every keyword position. PyCharm registers no `codeBlockSupportHandler` for Python either, so there was nothing to inherit. The highlight factory is `order="first"`, ahead of the platform's `LspHighlightUsagesHandlerFactory`, which claims every caret in a `.by` file because `by` advertises `documentHighlightProvider` and then highlights nothing on a keyword

Gated on the project carrying a basedpython marker, because `.html` is the most common extension there is; `buff` is unchanged and stays python-only
  - [ ] Ask the server which documents it serves, rather than duplicating its rule. Not possible today: LSP has no such request, the only file scoping in the protocol is a `documentSelector` on a *dynamic* registration, and `by` registers nothing for text documents — probed against 0.0.1, `initialize` returns `capabilities` and `serverInfo` with no `experimental` block, and its one registration is `didChangeWatchedFiles` with `globPattern: "**"`. It would also arrive too late, since this is what decides whether to start a server at all. One case the duplicated rule gets wrong meanwhile: a `TEMPLATES[*]["DIRS"]` pointing somewhere not called `templates` is served by the server and not offered by the plugin. Needs the server to advertise a document selector
- [x] Completion, hover, goto def/decl/type, references, rename, signature help, diagnostics, inlay hints, semantic tokens, code actions, symbols, folding, type hierarchy
- [x] **Push-to-hint** — each kind of hint is *never*, *always*, or *only while a key is held*, the gesture Rider calls Push-to-Hint and VS Code spells `editor.inlayHints.enabled: offUnlessPressed`. Two settings over the same kinds rather than one switch, because the kinds are not read the same way: a parameter name is worth having in front of you, a `: T` on every binding is what most people want only when they are asking. Holding the key shows the union of both. The key is a modifier held, not a shortcut pressed, so it is not a keymap action — the action system only ever reports the press, and a binding here would swallow the keystroke from whatever else wanted it. `lsp.inlay.ByHintPush` (an app service) watches `getModifiersEx` on every input event through one `IdeEventQueue` dispatcher that never consumes anything, publishes the raw mask, and lets each hint decide with its own project's `ByPushKey` — so a split, a second project window and a differently-configured project all behave. Default `Ctrl+Alt` (VS Code's), the shortest combination that means nothing on its own in an editor; plain `Ctrl` is the platform's go-to-declaration underline. Instant both ways: an on-push hint's inlay is built with the rest of them and merely draws nothing until the key goes down (`ByInlayHintPresentation.shown` → `fireSizeChanged` → `Inlay.update()`), because the alternative — collecting on press and release — is a daemon pass and a round trip to `by` per keystroke, and the platform's inlay pass skips a file whose PSI has not changed at all. A hidden hint measures one pixel, the editor rejecting a zero-width inline element outright
- [x] A setting per kind of hint `by` computes, taken from the server rather than guessed at: `ty_ide::InlayHintKind` is what it builds and `InlayHintOptions` in `ty_server` is what it lets a client switch, and `lsp.inlay.ByHintKind` mirrors that list option for option (variable types, lambda parameter types, call type arguments, type argument names, numeric promotions, revealed types, inferred raises, call argument names, implicit parameters, implicit self, implicit arguments, inferred override, inferred variance, inferred reification), plus an *other* kind of the plugin's own so a hint a newer `by` sends is switchable the day it appears. **Never is enforced at the server**: the modes go out as `initializationOptions.inlayHints.*`, so a hint nobody will draw is not inferred rather than inferred and dropped (`by` has no `workspace/didChangeConfiguration` yet, so a change restarts the server — which is what the settings page already did, and what `by`'s own VS Code extension does). **Always against on push is client-side**, because LSP carries two kinds for the fourteen the server distinguishes: `ByInlayHints.shapeOf` recovers the rest from the label, which works because the labels are fixed strings (` raises T`, `  revealed: T`, `override `, `reified `, `out `/`in `, `[T]`, `: T`, `name=`) and the two LSP kinds separate `name=` on an argument from `T=` on a type argument. Two kinds `by` writes identically (a variable's type and a lambda parameter's; an implicit `self` and any other implicit parameter) cannot be told apart on the wire, so where their settings disagree the more visible one draws — see `ByHintModes.forShape`. The django-template kinds (`templateBindingTypes`, `resolvedTemplates`) are deliberately absent: this provider draws hints for basedpython files, and the platform's own LSP rendering, which would draw them in an `.html` template, is off for `by`. There is no return-type setting because `by` has no return-type hint — the old toggle stood for nothing
- [x] Inlay hints rendered in the **editor font**, at editor size, on the code's baseline, faded onto a faint tint of the editor background — the VS Code look, and a deliberate replacement of the platform's. The platform builds every LSP hint with `PresentationFactory.smallText`: UI label font at ~⅘ editor size inside a rounded grey pill. For a language whose hints are nearly all types that reads as something pasted onto the line rather than as the annotation it stands in for. `LspInlayHintCustomizer` can only enable, disable or filter — there is no hook for the presentation — so `lsp.inlay.ByInlayHintsProvider` (a `codeInsight.inlayProvider`) sends `textDocument/inlayHint` itself and paints through `ByInlayHintPresentation`, and `ByLspServerDescriptor` sets `LspInlayHintDisabled` so the two don't both draw. Disabling costs nothing on the wire: the `inlayHint` *client capability* is advertised unconditionally by the platform, so `by` still answers. Font and size come from the *editor's* scheme, so zoom / presentation mode / distraction-free carry the hints with them — which the platform's rendering cannot do, its font being the single global `Use editor font` checkbox. Colour is `BASEDPYTHON_INLAY_HINT` — **both** halves. Faded text alone was a bug, not a style: dimmed editor-font text is how the IDE draws code that does not run, so an untinted hint is indistinguishable from an unused import sitting on the same line (`unused_local: int` had the name and the hint in the same grey). The tint is the smallest mark that separates them, and is not the platform's opaque capsule — it is sized to the text box rather than the line box, barely rounded, and leaves the glyphs on the code's column. Both bundled schemes set the pair; any other scheme gets them derived — text faded 38% into the background, tint the background with 20% of that text colour mixed in, resolved per half so a theme that restyles only the text still gets a tint derived from *its* colour. Not registered under `Settings | Editor | Inlay Hints` on purpose (`isVisibleInSettings = false`): the three basedpython settings are the one source of truth
- [x] A record of what the inlay pass did, and a check for a hint drawn twice — `lsp.inlay.ByInlayAudit` (pure) behind `ByInlayAuditLog` (an app service), `ByInlayAuditListener` (a `DaemonListener`) and *Tools | basedpython | Dump Inlay Hint Record*. A doubled hint (`def f() → 1 → 1:`) has exactly three possible causes and they are indistinguishable on screen: the collector ran twice in one pass, `by` sent the hint twice in one reply, or the platform is holding an inlay the pass never handed it. Nothing can be told after the fact either — a presentation carries no history, and the next pass drops the extra silently (`InlayHintsUtils.produceUpdatedRootList` keeps as many as the new list has), which is what let the first of the three live for as long as it did. So each pass records the hints it added, which run of the collector added each one and where it sat in `by`'s reply, and the audit reads that against what the editor is drawing — read through the renderers' own `toString`, which is public API and answers with the presentations joined (`LinearOrderInlayRenderer` → `SequencePresentation` → `[a b]`, the wrappers in between delegating down to `ByInlayHintPresentation.toString`), so an inlay holding two copies says so without reflection or a `@TestOnly` accessor. Drawn *fewer* times than collected is never a finding: an inlay can be waiting for a repaint or sitting at an offset an edit has moved, and neither is the bug. The daemon's finish is when the check runs — the only event that follows every way hints can change, with the pass applied by then — and it writes only when something is doubled, once per set of findings, because the daemon finishes far more often than the inlay pass runs. The action exists for the case the listener cannot serve: a doubling already on screen, which no further daemon run is coming for. Nothing is de-duplicated on the way in — a hint `by` sent twice is added twice, since quietly dropping it would hide the bug in the one place that can tell it apart from the other two

- [x] **A diagnostic's tooltip reads as the message it is** — `markup.ByCodeSpans` behind `lsp.diagnostics.ByDiagnosticsSupport` (on `by` and on `buff`, whose messages are written the same way). Every message the type checker writes names its types in markdown code spans, and the platform hands the message to `AnnotationBuilder.tooltip` unchanged — which takes HTML. So ``Object of type `<class 'int'>` is not callable`` reached the user as *Object of type `` `` is not callable*: the backticks shown as backticks, the type itself eaten by Swing's HTML parser as an unknown tag. The tooltip is now escaped, with a `<code>` per span; the *message* is untouched, since that is the plain-text side — Problems view, error stripe, *Copy problem description* — where backticks are simply how a type is quoted. Pairing the delimiters cannot be exact and does not pretend to be: `ty` never escapes the backticks that come out of the code being checked, so ``Type `Literal["`"]` is not assignable to `str` `` is genuinely ambiguous. Three rules bound the damage instead — a run matches a run of its own length (CommonMark, so a producer that *does* escape is read correctly), a span never crosses a line (one stray backtick can only spoil its own line), and a closer that would leave a `"` open is passed over for the next one, which recovers exactly the `Literal["`"]` case above and falls back to CommonMark's answer when no closer does better. The text is never altered or dropped, so the worst case is a fragment styled as prose that should have been code. The same renderer marks up the docstring in Type Info (`Ctrl+Shift+P`) — but not the type block above it, where a backtick is a character in a python string — and the two `by explain rule` balloons

- [x] **Environment management** — a "basedpython Environment" tool window that answers the question the interpreter dropdown does not: is there an environment, does it match what the project declares, and what do I press. Shows the backend, the environment's Python version (read from its own `pyvenv.cfg`, not by running the interpreter) and its dependency tree, over a banner that names the one problem worth fixing and the button that fixes it. Operations: create, sync, add, remove, upgrade-all, choose/install a Python version, and install the manager itself. `env.manager` — see below for the shape
  - **A grouped dependency tree, not a package list** — top level is *where a requirement is declared* (the main list, optional extras, named groups such as `dev`), second level is the requirements themselves, and below that is what each pulled in. A flat list cannot say which rows the project asked for versus which came along, nor which are test-only, and both change what the user does next. It also makes the operations exact instead of approximate: *Remove* is offered only on a declared requirement — a transitive one is not removable by any of these tools, and `uv remove urllib3` on a project that never declared it fails — and it removes from the right list, with a selection spanning groups becoming one command per group. *Add* targets the selected group, and a group that does not exist yet can be typed into the dialog and gets created
  - **The tree is the resolution, the flat list is the machine** — structure comes from `uv tree`, installed versions from `uv pip list`, and the view shows where they disagree: a package the environment does not have is greyed, one installed at a version other than the lock's is called out. That is drift made visible on the row it happens on, rather than as a banner asserting it. A package appearing under several requirements is expanded once per group and marked afterwards (per group rather than uv's global dedupe, so each group reads as a complete tree instead of one group arbitrarily winning the expansion)
  - **Reading the tree must not write to the project** — `uv tree` re-locks and writes `uv.lock` by default, verified against 0.12.3 on a project that had none, so the plugin always passes `--frozen`. Without it, opening a project would create a lock file and every save of `pyproject.toml` would rewrite it. A project with no lock has no resolved tree, the command exits non-zero, and the view falls back to the flat installed list — which is the correct answer for "nothing is resolved yet", not an error. `UvLiveBackendTest` asserts both directions against a real uv, since the flag being in the argv is not the same claim as uv honouring it
  - **The manifests are kept in step with the tools that rewrite them** — `uv add` / `uv remove` are separate processes that read `pyproject.toml` off disk and write it back, knowing nothing about the editor showing it, which leaves a gap on both sides. Before: unsaved editor changes are flushed, or uv reads the stale file and the user's edits vanish on the next read. After: the files are re-read (`refreshAndFindFileByNioFile` + `markDirtyAndRefresh`, off the EDT, the same pattern `GenerateApiFileAction` uses), including one the command created, or the editor sits on content that no longer exists — which is what a stale `pyproject.toml` after an Add actually was. Driven by `EnvBackend.managedFiles`, deliberately separate from `projectMarkers` because the two diverge for real backends (conda recognises `environment.yml` and never writes to it). The environment directory is *not* refreshed: thousands of files after a sync, and nothing here reads it through the VFS — `pyvenv.cfg` is read with `java.nio` precisely so a scan does not depend on VFS state
  - **Toolbar: one command that changes things, one that does not** — *Refresh* was removed from the toolbar and what remains is *Re-read*. Beside *Sync* it was a coin flip: both named after refreshing, both wearing a circular arrow, one installing packages over minutes and one re-reading state instantly. The view already re-reads on open, on any manifest change, and after every operation, so a permanent button for it existed mainly to be confused with the one that matters; it stays in the context and ⋮ menus for what the view cannot see (something installed straight into the environment). The *Python version* button carries its version as text (`Python 3.12`) rather than an icon — no platform icon means "Python interpreter" without the Python plugin, and the version answers "what am I on" while offering to change it — and its popup opens at the button rather than under the whole tree
  - **The index is cached, and Add Package uses it** — the package's summary, newest version and declared extras, the last being undiscoverable any other way (nothing short of a project's own docs tells you `httpx` offers `http2`). Extras render as checkboxes and write back into the requirement, inserted after the name and before any specifier — `httpx>=0.27` + `http2` is `httpx[http2]>=0.27`. A second seam, `PackageIndex`, separate from the backend because which *manager* runs a project and which *index* it installs from are independent. Cached under `~/.basedpython/cache/index/<index-id>`, keyed so a private mirror never gets served the public catalogue; catalogue refreshed weekly, per-package metadata daily; nothing fetched until the dialog opens. The catalogue is 872,009 names / 42 MB of JSON, so it is streamed with a token reader, stored as a sorted file, and prefix-searched with a binary search over byte offsets — as a `List<String>` it would be ~40 MB of permanent heap for data read only while a dialog is open. Verified against the real PyPI behind `BASEDPYTHON_ALLOW_NETWORK_TESTS=1`; the fixtures are verbatim PyPI documents, which is how a live test caught `provides_extra: null` (i.e. most packages) throwing away the summary and version along with the extras
  - **Live per-package progress** — a spinner and a state (*downloading / installing / removing*) on each row as an operation works through it, plus the current package and its size in the header. Driven by the tool's own output rather than guessed: uv reports `Downloading scipy (19.5MiB)` and ` Downloaded scipy` as they happen even when piped (verified on a cold cache), so concurrent downloads each animate their own row. Two honest gaps: a cached package is never downloaded and so never spins, and uninstalls are announced only in the trailing `-` block, so removals are marked before the command starts. Parsing lives in `EnvProgress`, off the same lines the log shows, so the spinner and the log can never disagree
  - **Pre-releases are named, not implied** — an index's `info.version` is its newest *stable*, so a package like `basedpython` (one ancient `0.0.0` under eight `0.0.1aN` alphas) reads as abandoned if that field is trusted alone. The summary names the newest pre-release when it exceeds the index's latest, and each pre-release row is labelled; both are shown because a resolver picks neither by accident — `latest` remains the default and pinning is the only route to an alpha. The real PyPI document for `basedpython` is a test fixture, since it is the shape that exposed this
  - **A version picker that says what is wrong with a version** — releases newest-first from the index, with a yanked release (PEP 592) marked and carrying the maintainer's reason, and one whose `requires_python` the environment fails marked with what it needs. Nothing is filtered: a version absent with no explanation is a puzzle, one labelled "needs Python >=3.14" is an answer. Picking pins with `==`, preserving ticked extras — the extras and version controls write to different parts of one requirement string and are tested composing in either order. Needs real PEP 440 (`Pep440`): string sorting puts `1.9` above `1.10`, and urllib3's actual `>=2.7, !=3.0.*, !=3.1.*, !=3.2.*, !=3.3.*, <4` is not answerable any other way. Release segments, epochs, pre-releases/`post`/`dev`, and `== != <= >= < > ~= ===` with `.*` wildcards and comma-AND; an unreadable clause counts as *satisfied*, since hiding a good release behind a gap in our own parser is the worse failure
  - **A results list, not an editor completion** — the field is plain text with a filtered list beneath it, repopulated in place rather than torn down, which is why it no longer blinks per keystroke; `ScrollingUtil.installActions` makes Up/Down from the field drive the list. This replaced a `TextFieldWithAutoCompletion`, and the replacement is the point: four separate defects came from the completion API's defaults, not from packages — autopopup never fires unless the provider overrides `acceptChar` (the platform's returns null); both available matchers accept far more than a prefix (camel-hump takes subsequences, and `PlainPrefixMatcher(prefix)` is `containsIgnoreCase`, so `ba` matched `b-aws-dynamodb-backup` two different ways); and a lookup assumes a short prefix's answer contains a longer prefix's, which a capped query over 872,009 names cannot promise, so correctness required `restartCompletionOnAnyPrefixChange` and that restart *is* a teardown. PyCharm's own package dialog is a field with a list for the same reasons. The filter is `EnvPackageSearch`, plain and tested
  - **The cold-start race is the one that bites** — opening Add starts the catalogue download, and typing during it used to ask a catalogue that did not exist and get an empty list, rendered as "No suggestions" while Ctrl+Space seconds later returned the right names. Callers now share one `CompletableFuture` per index and a lookup that needs the catalogue awaits it via `ProgressIndicatorUtils.awaitWithCheckCanceled`, inside the non-cached pass that `TextFieldWithAutoCompletionListProvider` already runs on a pooled thread under a `SensitiveProgressWrapper` — so blocking there is what the API is built for and the next keystroke cancels it. `getAdvertisement` says "Downloading the package list…" meanwhile, because an empty list with no explanation is what made a working feature look broken
  - **uv's tree JSON is a `preview` schema** — read defensively throughout, and anything unrecognised yields *no* tree rather than a partial one: a half-parsed graph would silently claim a project has fewer dependencies than it does. No tree degrades to the flat list, which is always truthful
  - **Pluggable by construction, uv-only today** — `EnvBackend` is the seam: a backend decides which projects it claims, where the environment goes, what argv each `EnvOp` becomes, and how to parse its own output. Adding conda or pixi is writing one object and adding it to `EnvBackends.ALL`; the service, the tool window, the actions and the banner are all written against the interface and would not change. Ordering in that list is most-specific-first, because a `pixi.toml` project also has a `pyproject.toml` — uv is last for that reason, not because it is least preferred. An op a backend cannot express returns null and the button is hidden rather than offering something that fails
  - **Still never automatic** — the rule above holds: nothing on this path runs because a project was opened. The service reports (two `stat`s, one small text file, and — only when an environment exists — a package list and a `uv sync --check` drift probe); `EnvOperations` acts, and only from a user gesture
  - **One button, three states** — *Set Up* installs the tool, creates the environment and syncs it, as far as this project needs, because those are steps of one job and a project two steps from working should take two steps rather than two visits to the tool window
  - **uv can install itself** — `~/.basedpython/bin`, the same plugin-managed directory the `by`/`buff` download uses. The release archive is fetched and one entry unpacked; uv's documented `curl … | sh` is not something this plugin does to a machine on a button press. No shell profile is edited and no `PATH` is changed — `EnvTools` looks in that directory directly, ahead of `PATH`, then in `~/.local/bin` and `~/.cargo/bin`, which is what fixes the most common report of all: an IDE started from a launcher inherits the session `PATH`, not a login shell's, so the uv the user installed is frequently invisible to it
  - **Everything that cached the answer is told** — creating or syncing an environment is exactly when `by` starts or stops resolving, so both language servers are restarted and editor notifications recomputed afterwards. The "by not found" banner and the `uv sync` action were each spawning uv themselves and doing none of this, which is how a successful install could leave the editor still insisting the binary was missing; both now go through `EnvOperations`
  - **Verified against a real uv** — `UvLiveBackendTest` (gated on `BASEDPYTHON_UV_UNDER_TEST`) drives uv 0.12.3 through create → sync → drift → add → list → remove → drift → python-list using the plugin's own argv and parsers, so a renamed flag or a changed exit code fails the build rather than the user's first click. The unit tests' JSON fixtures are verbatim uv output for the same reason
- [x] **Project structure — modules, in the settings** — *Settings | Languages & Frameworks | basedpython | Modules*: the parts a project is built from, listed with their type, path, version, `requires-python` and — the column the page exists for — which siblings depend on them. Create a module, change one, remove one. A module is what uv calls a workspace member: a directory with a `pyproject.toml` of its own, sharing the project's lock file and environment, importable by its siblings. `env.modules`
  - **A settings page rather than a fifth tool window** — because of what it is. The shape of a project is a thing you open, change and close, which is what the platform's own *Project Structure* dialog is; the environment view is a state you watch. A permanent stripe button for a screen visited when a module is added is a standing cost for an occasional gesture
  - **Nothing waits for *Apply*, and the page says why** — creating a module runs `uv init`, which writes files and edits the project's manifest; removing one can delete a directory. Queueing those behind *Apply* would mean a *Cancel* that cannot undo what it appears to, and a second implementation of every operation that pretends. So `isModified()` is always false, the table is a render of what is on disk, and the buttons act — the same rule the environment tool window follows, which is what makes the two impossible to disagree
  - **uv does everything uv can do** — `uv init <path>` scaffolds the module *and* lists it in `[tool.uv.workspace] members`, creating that table when the project has none, so a single-package project becomes a workspace by adding its first module and the plugin never writes a member entry itself. `uv add --package <module>` / `uv remove --package <module>` wire a module into a sibling, including the `[tool.uv.sources] … { workspace = true }` entry that makes the dependency resolve locally. All three behaviours are asserted against a real uv in `UvModuleLiveTest`, because none of them is in `uv init --help` and nothing else would notice them changing
  - **Two edits uv has no command for, and no more than two** — un-listing a module (uv adds a `members` entry and never removes one) and setting a project's own version / description / `requires-python` (uv reads those and never writes them). `TomlEdits` rewrites the lines the entry occupies and nothing else: comments survive, arrays keep their shape, CRLF stays CRLF, and a table the file does not have is left alone rather than invented. Round-tripping the document through a parser would reformat a file a person wrote, for a change of one value
  - **Un-listing is two different edits, and which one depends on how it was listed** — an exact `members` entry is removed; a glob is left alone, because it names the module's siblings too. When the files are being deleted the glob stops matching by itself; when they are being kept, the path joins `exclude`, which is uv's own way of saying "not a member" without changing what the glob means for anything else. Deleting the files is a checkbox, **off by default**, exactly as the platform's own *Remove module* behaves
  - **Removal starts with the dependents** — every sibling that declares the module stops declaring it first, in *each list* it declared it in: `uv remove` without the group flag takes a requirement out of the main list and reports success, leaving `dev` naming something that is gone. The dialog names those modules rather than counting them, because "remove this" and "remove this and stop `web` and `cli` depending on it" are different decisions
  - **The scan is bounded by the patterns, not by the repository** — a member glob is split at its first wildcard and walked from the literal part, no deeper than its remaining segments, with `.venv`, `out`, `dist`, `node_modules` and dot-directories pruned outright. A `**` member pattern would otherwise walk an environment holding a `pyproject.toml` for every installed distribution and report a project's dependencies as its modules. Read on the same refresh as everything else and carried on `EnvStatus`, so the page, the tool window and the next command describe one instant
  - **Names are compared the way packaging compares them** — PEP 503 normal form, so a manifest declaring `my_lib` is found to depend on the module called `my-lib`. Comparing raw strings reports a module as having no dependents right up until removing it breaks one
  - **Rename, including the imports in code** — six edits in one gesture: the import package under `src/`, the module's directory, `[project] name`, the `members` entry, every sibling that declares it (`uv remove` then `uv add`, so uv rewrites `[tool.uv.sources]` itself), and the `import` statements across the project. That last one is the part no editor can do alone, and it is asked of `by` through the protocol's own `workspace/willRenameFiles` — implemented in the server for this feature (`ty_ide::module_rename`, `ty_module_resolver::path_to_module_name`), because resolving every import in a project against the checker's own search paths, and telling a *use* of a module apart from a local variable spelled like it, are questions only the checker can answer. The request goes out **before** anything moves, which is what makes it answerable: the old path still holds the module. The six steps run in the one order where each can still see a project that makes sense — the imports first, then the siblings un-declare it while the workspace still resolves, then the directories move innermost-first (the import package lives inside the module directory), then the two manifests, then the siblings declare it again under the new name
  - **The name field is editable exactly when the server can answer** — `ModuleImportEdits.isSupported` reads `workspace.fileOperations.willRename` out of what `by` said at startup, and an older binary gets the field disabled with the reason rather than a rename that moves a directory and leaves every `import` naming the old one. What follows the name is decided rather than assumed: the directory is renamed only when it was named after the module (`packages/legacy-thing` stays put), and it keeps the spelling it had — a directory called `my_lib` for the distribution `my-lib` was following the *import* spelling and goes on following it. `ModuleRenamePlan` decides all of that as a pure function, because every one of those rules is a way to quietly restructure somebody's project while claiming to rename one thing
  - **The command is on screen** — *New module* renders the `uv init` it is about to run and updates it as the fields change, the same way the environment view streams uv's output into the log rather than reporting "done". A wizard that hides which flags it picked is one whose result cannot be predicted or reproduced. `--vcs none` and `--no-pin-python` are among them and are not preferences: without the first uv initialises a *second* git repository inside the project, and without the second every module gets a `.python-version` that can disagree with the project's
  - **It does not sync** — creating a module leaves the lock file describing a project with one fewer, and the honest response is the one the environment view already gives: report the drift, offer the button. Resolving — which can reach the network and download an interpreter — off the back of "I made a new directory" is what the plugin's uv rule exists to prevent. Adding the module as a dependency of another *does* sync, because that is `uv add`'s own doing and it is what was asked for
- [~] WSL / remote interpreter / Docker target support — `by`/`buff` commands honor a configurable working dir + env; running against a remote/Docker target needs the platform's `TargetEnvironment` API wired through every process launch + remote binary resolution. BLOCKED on the same missing-Python-SDK infra (no bundled Python plugin in IU-261 to reuse its target providers); a from-scratch target integration is out of scope for the LSP-first design

- [x] **Debugger** — source-mapped IDE debugging of `by run` *and* test configurations (a test run is a `by run pytest -v`, so the same bootstrap, interpreter and maps apply — verified live with a breakpoint in a `.by` test): line breakpoints in `.by` files, stepping, frames, variables and expression evaluation, all reported against `.by` sources. Built on the platform's DAP client (`intellij.platform.dap`) plus `debugpy`. `by run` writes `_by_sourcemap.py` (generated line → `.by` line, per file) into its temp directory; a `sitecustomize.py` injected through `PYTHONPATH` reads it, starts `debugpy` and reports back, and the IDE inverts it into runs and registers them with pydevd's `setPydevdSourceMap` — the translation happens in the debuggee, because IntelliJ's DAP client offers no hook to remap a breakpoint's line on the way out. Needs `debugpy` (`uv add --dev debugpy`): `by run` chooses `PYTHON`, else `python3` on `PATH`, and since every `by` launch here carries venv activation that resolves to the project's own interpreter (confirmed live); a missing one is reported with that interpreter's path and its `pip install` line. Breakpoints work in a project's plain `.py` files too, and need no source map to: `by run` transpiles only `.by`, so a `.py` module is loaded from where it was written and the file a breakpoint names is the file that runs. Two things made it work — `ByBreakpointFiles`, which lets the line breakpoint type claim a `.py` exactly when this plugin owns the file type (in PyCharm the Python plugin's type is one a DAP session can never see, because the platform dispatches a breakpoint to a handler by exact type class, and claiming a file PyCharm owns would put a "choose a type" popup on every gutter click); and the run's working directory on `PYTHONPATH`, because `by run` makes its temp tree `sys.path[0]` and a mixed project otherwise died on `ImportError: No module named 'helper'` before any debugger was involved. Verified live against debugpy 1.8.21 with a mixed project: the `.py` breakpoint stops with locals bound while the `.by` frames below it stay mapped. Remote targets are out of scope — see [docs/debugging.md](docs/debugging.md)

- [x] Gutter run icons on `if __name__ == "__main__"` / top-level
- [x] Run / check configurations and gutter icons on the plain `.py` files this plugin owns (`lang.dialect.BasedPythonSources`, the one predicate the run producers, the run marker and the breakpoint type all ask). `by run` transpiles only `.by`, so `by run pkg.script` starts `pkg/script.py` from where it was written — which is also why a breakpoint in it needs no source map (§64). Two asymmetries are deliberate: a `.py` beside a `.by` of the same module name is declined, because `by run` makes its temp tree `sys.path[0]` and would start the transpiled one; and a bare `def main(…)` in a `.py` gets no icon and no argument form, because reading a top-level `main` as the command line is a *basedpython* transform — the interpreter runs a `.py` as written, so an unguarded `main` is a function nothing calls (confirmed by running both: the `.by` printed its greeting, the `.py` printed nothing)
- [x] **`main`'s parameters, asked for as a form** — a top-level `main` *is* the program's command-line interface: basedpython builds an argparse parser from the signature (`str`/`int`/`float`/`bool`/`Path`, `bool` as a `--flag` / `--no-flag` pair, an underscore accepted both as `--out-dir` and `--out_dir`) and appends the guard that feeds it. So Run on a `def main(a: int)` used to produce the answer argparse gives — `error: the following arguments are required: a`, exit 2 — where the question belonged. It now **asks**: `ByRunConfiguration.getState` opens the form when, and only when, the run could not otherwise start, and returns null if it is cancelled, which both the run and debug runners take as "this run cannot start" and drop silently (`DefaultRunProgramRunner` / `AsyncProgramRunner` both check). Deliberately not `checkSettingsBeforeRun`, which looks like the hook for this and is not: the platform also calls it from `RunConfigurationIconAndInvalidCache` to decide whether a configuration's icon should look broken, so a dialog there would open when nobody asked to run anything. The form is generated from the signature — a file chooser for a `Path`, a three-state box for a `bool`, the docstring as its description (it is the parser's `--help` text), an `int` rejected before the transpile rather than after it, and an untouched optional parameter passing nothing rather than restating its default. The command line stays visible and editable at the bottom, and a hand-written one takes over rather than being reduced to the fields that fit it. Signature reading is textual (`run.main.ByMainSignature`), for the reason the test declarations are: the PSI for `.by` is one leaf per token
  - Asked **once per program**, not once per run: the answer is remembered against the module, and `ByRunFromFileProducer` seeds the next context configuration from it, so the green icon stays one click and runs the program the way it was last run. It is a real field on the configuration (*Program arguments*, with the same form behind the button) rather than a hidden side channel — distinct from *Extra args*, which belongs to `by run` itself
  - **Run with Arguments…** in the gutter is therefore not the way out of a run that cannot start — Run handles that itself — but the way to *change* arguments a run would otherwise reuse without asking. It sits after Run and Debug, and opens the same form
  - `run.main.ByMissingArgumentsHint` is the backstop for every path that does not go through the gutter — a saved configuration, a signature this failed to read, a future `by` that exposes parameters differently: it watches for argparse's own complaint and prints a **Run with arguments…** link under it that opens the same form and re-runs
  - The silent case has its own answer: a required parameter the command line *cannot* supply (`def main(db: Database)`) means basedpython emits no guard at all, so the module runs and does nothing. No form is offered there — the gutter tooltip says why instead, which is otherwise invisible

  - [x] **Reset Frame**, under bpd, on **any** frame in the stack — `debug.ByRestartFrameHandler`, through `XDebugProcess.getDropFrameHandler`. `restartFrame` is a DAP request bpd implements and advertises, and the platform's DAP client wires neither end of it (`intellij.platform.dap` names neither `restartFrame` nor `XDropFrameHandler`), so the action was grey no matter what the adapter said. It is not the JVM action it is named after: python cannot pop a frame, so bpd either runs the frame again **where it stands** — same frame object, caller untouched, and the locals a fresh call would not have bound put back to unbound rather than to `None` — or forces it to return and runs the caller's line again, which builds a frame that has never run. Measured: `work(n)` stopped with `n` mutated from `1` to `101` takes the second route, because a frame that has written over a parameter has lost what the call passed, and comes back with `n` at `1`. A frame below the top is reached by forcing the frames above it out, innermost first; they are gone rather than suspended. Which route a request gets, and every refusal, is decided by bpd off the bytecode of the frames involved and answered as an error response this handler reports — the plugin asks nothing about which frame it is. Offered on the **advertised capability** rather than on `ByDebugBackend` — debugpy reports `supportsRestartFrame` false — and asked live, because capabilities arrive after `initialize` and a decision taken at construction would answer "not yet" forever
  - [x] **Hot reload**, under bpd — `debug.hotswap`, on the platform's own `com.intellij.xdebugger.hotswap` extension point (`hotSwapInDebugSessionEnabler`). Everything visible is the platform's — the floating toolbar that appears over the editor the moment a tracked file stops matching what is running, its button, `XDebugger.Hotswap.Modified.Files` and the success balloon — and PyCharm registers no other implementation of that point, so this is the only one in the IDE. **Nothing you edit is the file that is running**: `by run` transpiles the project into a temp tree, copies every other project file in beside it, and runs out of there, so a `.by` was transpiled and a hand-written `.py` was *copied* — measured, both `__file__`s report from `/var/folders/.../T/.tmpXXXX/`. So both take one route. Pressing the button **saves** the edited documents first (the platform's collector tracks documents, a replacement is made from files, and nothing in between saves — so an unsaved edit used to come back `applied` with nothing changed and be reported as a successful reload), asks `by` through the language server what each file's slot in the running tree should now hold (`by/transpileForBuild` — the server holds the project database warm, which is why this is ~165ms rather than the 24.9s a full `by build` of a 97-file project costs; it returns bytes and writes nothing), writes them into the tree while remembering every byte replaced, and sends **one** `bpd/replaceCode` over the lot with `remap` set. bpd compiles each file, walks the tree that comes out against the one the process is running, and assigns `function.__code__` on **every** function object that held the old code — the closure a factory handed out earlier included, which is what a heap walk gets and a namespace walk does not. Nothing is ever applied partially, now across the whole set rather than one file. `remap` is in the same message because re-staging rewrote `_by_sourcemap.py` too and every `.by` breakpoint is armed on a generated line from the table it replaced — and the agent holds the GIL for exactly one message, so three messages would leave two windows in which another thread's logpoint maps through a stale table. **A refusal puts the tree back**, byte for byte: a tree holding code the process is not running is one bpd would read `.by` lines out of, and it would be a state the plugin created rather than the user. Refusals and errors go to a **notification** tracked through the platform's `HotSwapStatusNotificationManager` (so the next hot swap clears them), not to the console's error stream; the console keeps the account of what an applied replacement changed — which functions moved and where to, how many function objects held each, what the map reload installed, and which breakpoints had to bind again

Discovery is nine file names read at the project root — no process is started to enumerate tasks, unlike the test view's `by run pytest --collect-only` — so a VFS listener re-scans on save (500 ms debounce) and the tool window makes itself available when a project grows its first config file
  - Commands are one place (`ByTaskCommands`, pure + tested): `pre-commit run <id>`, `prek run <id>` (the two differ in exactly one flag — `--hook-stage` vs `--stage` — which is why they are separate runners), `lefthook run <hook> --commands|--jobs <name> --no-tty`, `./pw <alias>`. A hook whose `stages:` exclude `pre-commit` carries its stage into the command, since a plain `run <id>` would skip it silently with a zero exit code. A lefthook `scripts:` entry has no CLI filter to select it (there is no `--scripts`), so its row runs the whole hook and says so in grey
  - Config files are parsed by hand (`ByYaml`, `ByToml`) rather than through the YAML/TOML PSI: the scan is a pure function of file text on a background thread, which is what makes it testable against real configuration and free of read actions. Both document what they do not do (anchors/aliases/multi-document, dotted keys/array-of-tables) — none of it reachable from these schemas
  - Runners resolve through `ByEnvironments.resolve`, so a project's own `.venv/bin/pre-commit` beats a global install; pyprojectx is the exception and runs the checked-in `./pw` (chmod-ed via `Executables` if the mode bit was lost), falling back to `px` on `PATH`. `.pre-commit-config.yaml` is offered under `prek` when that is the only one of the two installed (`ByTaskRunners.preferred`)
  - *All files* is a persisted project preference, defaulted on: a hook run from a tool window with nothing staged inspects nothing and reports success
